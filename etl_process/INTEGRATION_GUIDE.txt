================================================================================

DATA FLOW:
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│  OLTP (PostgreSQL) ──Logical Decoding──> Debezium ──> Kafka Topics        │
│                                                              │              │
│                                                              ▼              │
│                                              Python ETL Pipeline            │
│                                          (Kafka Consumer + Transformers)    │
│                                                              │              │
│                                                              ▼              │
│                                                   OLAP (PostgreSQL)         │
│                                                                             │
│  Orchestration: Apache Airflow (daily batch jobs)                         │
│  Monitoring: Prometheus + Grafana                                         │
│  Logging: ELK Stack (Elasticsearch, Logstash, Kibana)                     │
└─────────────────────────────────────────────────────────────────────────┘

COMPONENT RESPONSIBILITIES:
- Debezium: Captures data changes from OLTP (INSERT, UPDATE, DELETE)
- Kafka: Message broker storing CDC events for fault-tolerant processing
- Python: Transforms Kafka events and loads into OLAP
- Airflow: Schedules batch jobs, monitors pipeline health
- Dimension Tables: Store slowly changing dimensions (SCD Type 2)
- Fact Tables: Store granular transactions and aggregated analytics

STEP 2.1: ENABLE LOGICAL DECODING ON OLTP POSTGRESQL
─────────────────────────────────────────────────────

Logical decoding allows Debezium to capture changes without replication slots
becoming a bottleneck.

Prerequisites:
  - PostgreSQL 10+ (we're using PostgreSQL 13+)
  - Superuser access to modify postgresql.conf
  - Planned restart or use ALTER SYSTEM for runtime changes

Configuration Changes:
  1. Modify postgresql.conf:
     - Set: wal_level = logical
     - Set: max_wal_senders = 10
     - Set: max_replication_slots = 10
     - Set: shared_preload_libraries = 'decoderbufs'
     
  2. Restart PostgreSQL:
     $ sudo systemctl restart postgresql
     
  3. Create replication slot (Debezium will use this):
     SELECT * FROM pg_create_logical_replication_slot('debezium_slot', 'test_decoding');
     
  4. Verify logical replication:
     SELECT * FROM pg_replication_slots;
     
  5. IMPORTANT: Enable Publications for specific tables:
     CREATE PUBLICATION debezium_pub FOR TABLE Users, Accounts, Orders, Executions, 
                                         Trades, Transactions, Disputes, Cash_Ledger;

STEP 2.2: KAFKA CLUSTER SETUP
──────────────────────────────

Kafka will store CDC events as immutable log for fault tolerance.

Broker Configuration:
  - Min brokers: 3 (for HA and fault tolerance)
  - Replication factor: 3
  - Min in-sync replicas: 2
  - Retention policy: 7 days minimum (or adjust based on processing speed)

Topic Creation Script (kafka-topics-init.sh):
  - Create topics for each OLTP table:
    * debezium.oltp.public.users
    * debezium.oltp.public.accounts
    * debezium.oltp.public.account_cash_balances
    * debezium.oltp.public.securities
    * debezium.oltp.public.orders
    * debezium.oltp.public.order_reservations
    * debezium.oltp.public.executions
    * debezium.oltp.public.trades
    * debezium.oltp.public.transactions
    * debezium.oltp.public.cash_ledger
    * debezium.oltp.public.account_positions
    * debezium.oltp.public.disputes
    
  - Topic-specific configurations:
    * Partitions: 6 (for parallelism)
    * Replication factor: 3
    * Retention: 7 days
    * Compression: snappy (good for JSON CDC events)

Topic Configuration Template:
  kafka-topics --create \
    --topic debezium.oltp.public.[TABLE_NAME] \
    --partitions 6 \
    --replication-factor 3 \
    --config retention.ms=604800000 \
    --config compression.type=snappy \
    --bootstrap-server localhost:9092

STEP 3.1: OLTP SETUP (PostgreSQL - Source)
───────────────────────────────────────────

Ensure OLTP database has:
  1. All base tables created with proper constraints
  2. Primary keys on all tables (required for CDC)
  3. Unique constraints where necessary
  4. Foreign key relationships documented
  5. Check constraints for enum values
  6. Logical decoding enabled (see Phase 1)
  7. Dedicated user account for Debezium:
     CREATE USER debezium_user WITH PASSWORD '[SECURE_PASSWORD]';
     GRANT CONNECT ON DATABASE oltp_db TO debezium_user;
     GRANT USAGE ON SCHEMA public TO debezium_user;
     GRANT SELECT ON ALL TABLES IN SCHEMA public TO debezium_user;

STEP 3.2: OLAP SETUP (PostgreSQL - Target)
────────────────────────────────────────────

Before loading any data, OLAP must have:

  1. Base dimension and fact tables created
  2. Schema version tracking table:
     CREATE TABLE schema_version (
       version VARCHAR(10) PRIMARY KEY,
       description TEXT,
       applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
     );
     
  3. Slowly Changing Dimension (SCD Type 2) tables with:
     - [Business_Key] BIGINT
     - SCD_Start_Date DATE
     - SCD_End_Date DATE (nullable)
     - Is_Current BOOLEAN
     
  4. Fact tables with appropriate grain:
     - fact_daily_trading_summary (grain: date + security + exchange)
     - fact_account_daily_activity (grain: date + account)
     - fact_sector_daily_performance (grain: date + sector)
     
  5. Materialized views for common queries:
     - vw_top_securities_by_volume
     - vw_top_accounts_by_activity
     - vw_top_sectors_by_value
     
  6. Dedicated user for Python ETL:
     CREATE USER etl_user WITH PASSWORD '[SECURE_PASSWORD]';
     GRANT CONNECT ON DATABASE olap_db TO etl_user;
     GRANT USAGE ON SCHEMA public TO etl_user;
     GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO etl_user;
     GRANT ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA public TO etl_user;
     
  7. Pipeline tracking table:
     CREATE TABLE etl_pipeline_runs (
       run_id BIGSERIAL PRIMARY KEY,
       dag_name VARCHAR(100),
       task_name VARCHAR(100),
       start_time TIMESTAMP,
       end_time TIMESTAMP,
       status VARCHAR(20),
       rows_processed INT,
       error_message TEXT,
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
     );
     
  8. Initial data load strategy:
     - First load from OLTP via INSERT SELECT (bulk copy)
     - Then stream CDC changes via Kafka
     - Validate record counts match between OLTP and OLAP

STEP 3.3: DATA SYNC STRATEGY
─────────────────────────────

Initial Load (Full Snapshot):
  1. Use Debezium snapshot mode = 'initial'
  2. Debezium will read all tables in OLTP and load into Kafka topics
  3. Python consumer reads snapshot events and loads to OLAP fact tables
  4. After snapshot complete, Debezium switches to incremental CDC mode
  
Incremental Changes:
  1. Debezium captures INSERT/UPDATE/DELETE from OLTP logical logs
  2. Changes arrive as JSON events in Kafka topics
  3. Python consumer processes events near real-time
  4. Updates OLAP tables and refreshes affected fact table aggregations

Reprocessing Capability:
  - Keep Kafka topic retention at 7 days minimum
  - Store processing offsets in database for recovery
  - Allow re-processing from specific Kafka offset if needed

STEP 4.2: KAFKA CONSUMER IMPLEMENTATION

Consumer Responsibilities:
  1. Connect to Kafka broker using consumer group
  2. Subscribe to CDC topics (auto-discover new tables)
  3. Deserialize JSON CDC events
  4. Validate event schema (all required fields present)
  5. Handle poison pills (malformed messages)
  6. Batch process events (collect 1000 events or 30 sec, whichever first)
  7. Commit offsets only after successful processing
  8. Monitor lag and alert if lag exceeds threshold

Configuration:

  - auto_offset_reset: 'earliest' (to replay if needed)
  - enable_auto_commit: False (manual commit for idempotency)

  - session_timeout_ms: 30000 (heartbeat to broker)
  - connections_max_idle_ms: 540000 (9 minutes)

Error Handling:
  - Retry logic with exponential backoff (3 attempts, max 60 seconds)
  - Send poison pill events to dead-letter topic for manual review
  - Log all errors with context (event data, timestamp, consumer offset)
  - Implement circuit breaker for OLAP database connection failures

STEP 4.3: DATA TRANSFORMATION LAYER
────────────────────────────────────

Transformer Classes:
  - BaseTransformer (abstract class with common methods)
  - UserTransformer (handle user dimension changes)
  - AccountTransformer (handle account dimension changes)
  - OrderTransformer (normalize order data)
  - ExecutionTransformer (normalize execution data)
  - TradeTransformer (normalize trade data)
  - TransactionTransformer (normalize transaction data)
  - DisputeTransformer (handle dispute data)
  
Each Transformer Must:
  1. Validate incoming CDC event schema
  2. Map OLTP column names to OLAP column names
  3. Transform data types (e.g., string dates to TIMESTAMP)
  4. Handle NULL values appropriately
  5. Implement business logic (e.g., side effect calculations)
  6. Generate audit trail (who changed what, when, why)
  7. Detect and handle duplicates (Kafka at-least-once delivery)
  8. Return structured output for loader

Transformation Rules by Table:

  Users → dim_user (SCD Type 2):
    - On UPDATE: If status, email, or name changed, close old record, add new record
    - Keep history of all status changes (ACTIVE → SUSPENDED, etc.)
    - Mark most recent as Is_Current = TRUE
    - Role_ID is now direct on Users table (no User_Roles junction)
    
  Accounts → dim_account (SCD Type 2):
    - Link to user via User_ID (no need to re-fetch user)
    - Track creation date changes
    
  Orders → fact_orders (grain: order):
    - Denormalize account, security info
    - Capture created vs updated timestamp
    
  Trades → fact_trades (grain: trade):
    - Include execution details (needed for drill-down)
    - Calculate trade value = price * shares
    
  Transactions → fact_transactions (grain: transaction):
    - Denormalize account, transaction type
    - Track transaction lifecycle (PENDING → COMPLETED or FAILED)
    
  Disputes → fact_disputes (grain: dispute):
    - Join transaction and trade if applicable
    - Calculate dispute aging metrics
    
  Securities → dim_security (SCD Type 2):
    - Track security status changes (ACTIVE, HALTED, DELISTED)
    - Quote_Currency mandatory, Base_Currency for FOREX only
    - Asset_Type: EQUITY, FOREX, CRYPTO
    
  Account_Cash_Balances → fact_cash_balance_snapshot:
    - Daily snapshot of account cash balances
    - Grain: date + account
    - Tracks Updated_At timestamp
    
  Order_Reservations → fact_order_reservations:
    - Track capital reservations for orders
    - BUY: Reserved_Cash populated, Reserved_Quantity NULL
    - SELL: Reserved_Quantity populated, Reserved_Cash NULL
    - Status: ACTIVE, CONSUMED, RELEASED
    
  Account_Positions → fact_account_positions_snapshot:
    - Daily snapshot of open positions
    - Grain: date + account + security
    - Quantity always > 0 (closed positions excluded)
    - Average_Price for cost basis tracking
    
  Cash_Ledger → fact_ledger (grain: ledger entry):
    - Track running balance changes (always >= 0)
    - Link to transaction and/or trade
    - Entry_Type: DEPOSIT, WITHDRAWAL, FEE, BUY, SELL

STEP 4.4: DATA LOADER IMPLEMENTATION
──────────────────────────────────────

Loader Responsibilities:
  1. Batch INSERT/UPDATE/DELETE operations (not per-event)
  2. Handle SCD Type 2 slowly changing dimensions
  3. Use UPSERT (INSERT ... ON CONFLICT) for idempotency
  4. Track processed events to prevent double-processing
  5. Validate data before insert (check constraints, FK integrity)
  6. Provide detailed load statistics (rows inserted/updated/rejected)
  7. Rollback on critical errors, log recoverable errors

SCD Type 2 Implementation:
  - On dimension UPDATE:
    * Set SCD_End_Date = current date on existing record
    * Set Is_Current = FALSE on existing record
    * INSERT new record with SCD_Start_Date = today
    * Set Is_Current = TRUE on new record
  
  - Example (User dimension):
    WITH new_record AS (
      SELECT User_ID, Name, Email, Status, 
             CURRENT_DATE as SCD_Start_Date, NULL as SCD_End_Date
      FROM staging_users
    ),
    update_existing AS (
      UPDATE dim_user
      SET SCD_End_Date = CURRENT_DATE - INTERVAL '1 day', 
          Is_Current = FALSE
      WHERE User_ID = (SELECT User_ID FROM new_record)
        AND Is_Current = TRUE
        AND (Name, Email, Status) != (SELECT Name, Email, Status FROM new_record)
    )
    INSERT INTO dim_user 
    SELECT *, CURRENT_DATE as SCD_Start_Date, NULL, TRUE 
    FROM new_record
    ON CONFLICT DO NOTHING;

STEP 4.5: IDEMPOTENCY & DEDUPLICATION
──────────────────────────────────────

Kafka provides at-least-once delivery, so deduplication is CRITICAL:

Strategies:
  1. Track processed Kafka offsets per table:
     CREATE TABLE kafka_offsets (
       topic VARCHAR(100),
       partition INT,
       offset BIGINT,
       processed_at TIMESTAMP,
       PRIMARY KEY (topic, partition)
     );
     
  2. Before processing batch, check if already processed:
     SELECT MAX(offset) FROM kafka_offsets 
     WHERE topic = ? AND partition = ?
     
  3. After successful load, store offset:
     INSERT INTO kafka_offsets VALUES (?, ?, ?, CURRENT_TIMESTAMP)
     ON CONFLICT (topic, partition) DO UPDATE
     SET offset = EXCLUDED.offset, processed_at = CURRENT_TIMESTAMP
     
  4. Use business key for duplicate detection in fact tables:
     - For trades: (Trade_ID) must be unique
     - For transactions: (Transaction_ID) must be unique
     - Use UNIQUE constraints or upsert logic

STEP 4.6: LOGGING & MONITORING
───────────────────────────────

Implement structured logging:
  - Use Python logging module
  - Log to file: logs/etl_pipeline_[YYYY-MM-DD].log
  - Include: timestamp, level (INFO/WARN/ERROR), component, message
  - For errors: include stack trace, event data (sanitized), recovery action
  
Metrics to Track:
  - Events consumed per minute
  - Processing latency (from Kafka to OLAP)
  - Kafka consumer lag (current offset vs latest)
  - Database connection pool health
  - Transformation error rate
  - Load success rate

Alert Thresholds:
  - Consumer lag > 10000 events → WARNING
  - Processing latency > 5 minutes → WARNING
  - Error rate > 1% → CRITICAL
  - Database connection pool exhausted → CRITICAL
  - Kafka broker down → CRITICAL (immediate)

     └─ Depends on: refresh_aggregates
     
  8. report_generation
     └─ Generate daily summary metrics
     └─ Email to analytics team
     └─ Store in reports table
     └─ Depends on: quality_checks
     
  9. monitor_pipeline_health
     └─ Calculate SLA metrics
     └─ Alert if any task failed
     └─ Log to monitoring system

6. PHASE 5: SCHEMA OPTIMIZATION FOR ANALYTICS
================================================================================

STEP 6.1: RECOMMENDED OLAP SCHEMA CHANGES
──────────────────────────────────────────

Current OLAP Issues & Fixes:

ISSUE 1: Missing Slowly Changing Dimension (SCD) Type 2 Support
  Current: Users, Accounts, Securities directly copied
  Problem: History is lost when records update
  Solution: Add SCD Type 2 columns to dimensions:
    ALTER TABLE dim_user ADD COLUMN scd_start_date DATE DEFAULT CURRENT_DATE;
    ALTER TABLE dim_user ADD COLUMN scd_end_date DATE;
    ALTER TABLE dim_user ADD COLUMN is_current BOOLEAN DEFAULT TRUE;
    CREATE INDEX idx_dim_user_current ON dim_user(User_ID, is_current);

ISSUE 2: Fact Tables Lack Degenerate Dimensions
  Current: fact_trades, fact_orders don't include order side/status
  Problem: Can't aggregate by side or status without joins
  Solution: Denormalize order details into fact tables:
    ALTER TABLE fact_trades ADD COLUMN order_side CHAR(1);
    ALTER TABLE fact_trades ADD COLUMN order_status VARCHAR(16);
    ALTER TABLE fact_trades ADD COLUMN account_id BIGINT;
    CREATE INDEX idx_fact_trades_account ON fact_trades(account_id);

ISSUE 3: No Date Dimension (dim_date)
  Current: Using raw dates from fact tables
  Problem: Can't aggregate by fiscal quarter, week number, etc
  Solution: Create comprehensive date dimension:
    CREATE TABLE dim_date (
      date_key BIGINT PRIMARY KEY,
      date DATE UNIQUE NOT NULL,
      year INT NOT NULL,
      quarter INT NOT NULL,
      month INT NOT NULL,
      month_name VARCHAR(10),
      quarter_name VARCHAR(10),
      week INT NOT NULL,
      day INT NOT NULL,

9. CRITICAL CONSIDERATIONS
================================================================================

CONSIDERATION 1: EXACTLY-ONCE SEMANTICS
────────────────────────────────────────

Problem: Kafka guarantees "at-least-once" delivery, so events may be processed twice.

Impacts:
  - Duplicate rows in OLAP fact tables
  - Incorrect aggregations if not handled
  - Data quality issues

Solutions:
  1. Track Kafka offsets per topic-partition
  2. Check if offset already processed before transforming
  3. Use INSERT ... ON CONFLICT for idempotency
  4. Use business key uniqueness constraints
  5. Implement poison pill handling (send to DLQ)

Recommendation: Implement all three strategies:
  - Offset tracking
  - Business key uniqueness
  - Deduplication logic

CONSIDERATION 2: SCHEMA DRIFT (OLTP Changes)
─────────────────────────────────────────────

Problem: When OLTP schema changes (add column), Debezium reflects change, Python breaks.

Impacts:
  - ETL pipeline fails if new column appears
  - OLAP schema may not match OLTP structure
  - Data loss if not handled

Prevention:
  1. Schema registry (Confluent Schema Registry)
  2. Version control for Python transformers
  3. Automated schema validation
  4. Coordinate OLTP changes with ETL team
  5. Have rollback plan for schema changes

Mitigation:
  - Add new columns as nullable in OLAP initially
  - Update transformers before OLTP schema deploys
  - Test transformers with new schema before prod

CONSIDERATION 3: SLOWLY CHANGING DIMENSIONS
────────────────────────────────────────────

Problem: SCD Type 2 requires complex logic to maintain history.

Impacts:
  - Queries become more complex (must filter is_current = TRUE)
  - JOIN logic needs careful design
  - Performance impact if not indexed properly

Solutions:
  1. Create automated SCD Type 2 procedures
  2. Index on (business_key, is_current)
  3. Use effective dating (SCD_Start_Date, SCD_End_Date)
  4. Document SCD logic in schema comments
  5. Test SCD handling with edge cases (same-day updates)

Recommendation: Build reusable SCD utility functions in Python.

CONSIDERATION 4: PARTITION MAINTENANCE
───────────────────────────────────────

Problem: As data grows, partitioned tables need ongoing maintenance.

Impacts:
  - Queries slow down if old partitions not managed
  - Disk space fills up
  - Administrative overhead

Solutions:
  1. Automate partition creation (create partition 1 quarter ahead)
  2. Automate partition archival (detach old partitions)
  3. Monitor partition sizes
  4. Document retention policy
  5. Test archival/restore procedures

Recommendation: Use Airflow task to manage partitions monthly.

CONSIDERATION 5: HANDLING LATE-ARRIVING DATA
──────────────────────────────────────────────

Problem: Trades/transactions may load days after they occur.

Impacts:
  - Daily aggregations become stale
  - Reports show incomplete data
  - Analysts trust wrong numbers

Solutions:
  1. Separate pipelines for "hot" (same-day) vs "cold" (late) data
  2. Re-aggregate when late data arrives
  3. Track data latency metrics
  4. Implement "restatement" flag in fact tables
  5. Communicate data freshness to users

Recommendation: 
  - Daily load for same-day trades (2 AM)
  - Nightly reload for trades from past 7 days (10 PM)
  - Monthly full audit (all trades)

CONSIDERATION 6: PERFORMANCE TUNING
────────────────────────────────────

Problem: OLAP queries slow down as data accumulates.

Impacts:
  - Dashboard latency > 10 seconds (bad UX)
  - Materialized view refresh takes > 1 hour
  - Report generation fails

Solutions:
  1. Proper indexing strategy (covered in PHASE 5)
  2. Partitioning by date (covered in PHASE 5)
  3. Aggregate tables instead of detail queries
  4. Query optimization (EXPLAIN ANALYZE)
  5. Connection pooling for Python
  6. Caching layer for dashboards

Recommendation:
  - Use aggregated fact tables for dashboards (not detail)
  - Partition all fact tables by date
  - Index on (date_key, dimension_key) patterns
  - Monitor query performance monthly

CONSIDERATION 7: SECURITY & COMPLIANCE
───────────────────────────────────────

Problem: ETL pipeline processes sensitive financial data.

Impacts:
  - Data breach risk
  - Regulatory compliance (SOX, GDPR, PCI-DSS)
  - Audit trail requirements

Solutions:
  1. Use encrypted connections (SSL/TLS)
  2. Credential management (rotate passwords)
  3. Row-level security (RLS) for OLAP queries
  4. Audit logging (who accessed what, when)
  5. Data masking for sensitive fields (SSN, card numbers)
  6. Regular security scans

Recommendation:
  - Store credentials in .env files or secret manager
  - Encrypt Kafka topics at rest
  - Enable PostgreSQL audit logging
  - Implement data retention policies

CONSIDERATION 8: COST OPTIMIZATION
───────────────────────────────────

Problem: ETL infrastructure can be expensive at scale.

Impacts:
  - Kafka cluster cost (brokers, storage)
  - PostgreSQL costs (OLTP + OLAP databases)
  - Compute resources (Python, Airflow workers)

Solutions:
  1. Right-size infrastructure for data volume
  2. Use cloud auto-scaling
  3. Archive old data to cheaper storage
  4. Optimize Kafka retention policy
  5. Use connection pooling to reduce DB connections
  6. Monitor and alert on runaway costs

Recommendation:
  - Start with 3 Kafka brokers, scale if lag persists
  - Use RDS or Cloud SQL for managed databases
  - Keep Kafka retention at 7 days (adjust based on lag)
  - Archive data older than 2 years to S3/GCS

11. TROUBLESHOOTING GUIDE
================================================================================

ISSUE: Debezium Connector Not Starting
─────────────────────────────────────

Symptoms:
  - Connector status shows ERROR
  - No events in Kafka topics
  - Connector logs show "Connection refused"

Diagnosis:
  1. Check Debezium logs: tail -f /var/log/debezium/debezium.log
  2. Verify OLTP PostgreSQL is running: psql -h localhost -U postgres
  3. Check replication slot exists: SELECT * FROM pg_replication_slots;
  4. Verify publication exists: SELECT * FROM pg_publication;
  5. Check Kafka broker connectivity: nc -zv kafka 9092

Resolution:
  1. If OLTP down: start PostgreSQL service
  2. If replication slot missing: CREATE replication slot (see PHASE 2.1)
  3. If publication missing: CREATE publication (see PHASE 2.1)
  4. If Kafka down: check Kafka broker logs
  5. Restart connector: curl -X DELETE http://kafka-connect:8083/connectors/postgres-oltp-connector
                       curl -X POST http://kafka-connect:8083/connectors -d @connector-config.json

ISSUE: Kafka Consumer Lag Growing
──────────────────────────────────

Symptoms:
  - lag > 10000 events
  - Airflow task taking longer than expected
  - Graphs showing upward trend in lag

Diagnosis:
  1. Check consumer lag: kafka-consumer-groups --group etl_pipeline_consumer_group --describe --bootstrap-server localhost:9092
  2. Check Python ETL processing rate: grep "records processed" etl_pipeline.log
  3. Check OLAP database load: vmstat or iostat
  4. Check network latency between Python and Kafka: ping kafka
  5. Check network latency between Python and OLAP: ping postgres-olap

Resolution (by cause):
  - If network latency high: Check network connectivity, move to faster cluster
  - If OLAP disk I/O high: Add indexes, optimize queries, increase disk throughput
  - If Python CPU high: Add more workers, optimize transformation logic
  - If Kafka broker slow: Scale Kafka cluster (add more brokers)
  - If temporary spike: Monitor for 24 hours, can catch up

ISSUE: Data Quality Check Failures
─────────────────────────────────

Symptoms:
  - Airflow quality_checks task fails
  - Alerts for duplicate rows, NULL values, etc
  - Analytics team reports incorrect numbers

Diagnosis:
  1. Check which quality check failed: grep "FAILED" quality_checks_[date].log
  2. Query the offending table: SELECT * FROM [table] WHERE [quality_check]
  3. Check when data was first invalid: Look at etl_pipeline_runs table
  4. Trace back to Kafka events: Check Kafka offset when problem started
  5. Check Python transformer logic: Review transformation rules for that table

Resolution:
  1. Fix root cause (usually data transformation logic)
  2. Insert corrected data if needed: UPDATE [table] SET [correct_values]
  3. Re-run quality checks
  4. Update analyst dashboard if showed bad numbers
  5. Document incident in postmortem

ISSUE: Python Pipeline Crashes
───────────────────────────────

Symptoms:
  - Python process exits unexpectedly
  - Airflow task logs show Python exception
  - No error message (or cryptic stack trace)

Diagnosis:
  1. Check Python error logs: tail -f logs/etl_pipeline_[date].log
  2. Look for stack trace: grep -i exception logs/etl_pipeline_[date].log
  3. Check system resources: free -h (memory), df -h (disk space)
  4. Check database connectivity: psql -h postgres-olap -U etl_user
  5. Check Kafka connectivity: python -c "from kafka import KafkaConsumer; KafkaConsumer('test', bootstrap_servers='kafka:9092')"

Resolution (by cause):
  - Out of memory: Reduce batch size, add more RAM
  - Out of disk: Clean up logs/temp files, expand storage
  - Database connection issue: Check credentials, verify DB is running
  - Kafka connection issue: Check Kafka broker status, verify bootstrap servers
  - Python exception: Fix code bug, test locally before deploying
  - Hung connection: Check network, implement connection timeouts

ISSUE: Airflow DAG Not Running on Schedule
───────────────────────────────────────────

Symptoms:
  - DAG scheduled for 2 AM but doesn't run
  - Airflow UI shows task not in queue
  - No logs for missed DAG runs

Diagnosis:
  1. Check Airflow scheduler is running: ps aux | grep "airflow scheduler"
  2. Check DAG parsing errors: airflow dags test [dag_id]
  3. Check DAG syntax: python [dag_file] (should not print anything)
  4. Check Airflow metadata DB: psql -d airflow_db
  5. Check system time/timezone: date && timedatectl

Resolution:
  - If scheduler not running: systemctl start airflow-scheduler
  - If parsing errors: Fix Python syntax errors in DAG
  - If timezone issue: Set TZ environment variable in airflow.cfg
  - If DAG not showing in UI: Wait 5 minutes for DAG parser to re-run
  - Manually trigger DAG for testing: airflow dags trigger [dag_id]

ISSUE: Materialized View Refresh Slow
──────────────────────────────────────

Symptoms:
  - refresh_aggregates task timeout
  - Materialized view refresh takes > 1 hour
  - Dashboards stale/empty after 2 AM

Diagnosis:
  1. Check view query complexity: \d+ [view_name] (in psql)
  2. Check table sizes: SELECT pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) FROM pg_tables WHERE schemaname = 'public';
  3. Run EXPLAIN ANALYZE on view query: EXPLAIN ANALYZE SELECT * FROM [view];
  4. Check for missing indexes: Review execution plan for "Seq Scan"
  5. Check data volume: SELECT COUNT(*) FROM fact_trades;

Resolution:
  - Add indexes on columns in WHERE/JOIN clauses
  - Partition fact tables (see PHASE 5)
  - Simplify view logic if possible
  - Increase Airflow task timeout
  - Refresh CONCURRENTLY (non-blocking) instead of REFRESH
  - Consider incremental refresh instead of full refresh

ISSUE: PostgreSQL Connection Pool Exhausted
─────────────────────────────────────────────

Symptoms:
  - Python error: "remaining connection slots reserved for non-replication superuser use"
  - Airflow task hangs/times out
  - All connections show "idle in transaction"

Diagnosis:
  1. Check active connections: SELECT * FROM pg_stat_activity;
  2. Check idle transactions: SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction';
  3. Check max connections: SHOW max_connections;
  4. Check Python connection pool: Check config.yaml pool_size and pool_recycle
  5. Check for connection leaks: Are connections properly closed after use?

Resolution:
  - Kill idle connections: SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle in transaction' AND query_start < NOW() - INTERVAL '30 minutes';
  - Increase max_connections in postgresql.conf (if not already high)
  - Implement connection pooling with PgBouncer
  - Fix Python code to close connections properly
  - Add connection timeout and recycle settings
  - Monitor connection count daily

ISSUE: Debezium Replication Slot Lagging
─────────────────────────────────────────

Symptoms:
  - Debezium warns: "slot is lagging behind WAL"
  - OLTP PostgreSQL disk fills up (WAL files accumulate)
  - Debezium connector stops consuming new events

Diagnosis:
  1. Check slot lag: SELECT * FROM pg_replication_slots WHERE slot_name = 'debezium_slot';
  2. Check WAL file count: ls -la pg_wal/ | wc -l (should be < 100)
  3. Check Kafka topics for backlog: kafka-consumer-groups --group [group] --describe
  4. Check Debezium connector status: curl http://kafka-connect:8083/connectors/postgres-oltp-connector/status
  5. Check OLTP write rate: Monitor transaction logs

Resolution:
  - Increase Python consumer parallelism (add workers)
  - Increase Kafka broker capacity (add brokers)
  - Reduce OLTP write volume if possible (batch writes)
  - Adjust Debezium batch size (max_batch_size)
  - Monitor WAL disk usage and alert if > 90%
  - In extreme case: drop slot and recreate (loses change history)
